# Observability source and function catalogue

This catalogue covers the significant public service functions for Feature 8. Exact FastAPI parameter schemas are generated from the running source at `/api/openapi.json`. Internal helpers prefixed with `_` are implementation details and are not a supported API. Database functions assume the observability schema has been initialized; callers should handle `ValueError`, `OSError` and `sqlite3.Error` at service boundaries.

## API and MCP boundary

`require_basic_admin(request, credentials)` in `main.py` validates the existing dashboard Basic credentials, enforces the in-memory failure rate limit, and emits coalesced `auth.login_failed` / `auth.login_succeeded` events without persisting submitted usernames, client addresses or credentials. It returns the administrator name or raises HTTP 401/429; successful login raises a sanitized 503 and does not run the requested dashboard action if neither the primary audit transaction nor the bounded fallback sidecar confirms the accepted-login event. Invalid-login and generic-denial outcomes remain rejected; if neither store retains their audit, their coalescing keys are cleared so a later matching attempt can retry. The fallback accepts only these three auth event types, reuses the standard details redactor, and replays with stable event IDs on startup/heartbeat. FastAPI handlers use this dependency directly or through `require_admin`; versioned API scopes, sensitive-read checks and control checks remain enforced by shared route dependencies. The shared API middleware records otherwise-unhandled 401/403 responses as coalesced `authz.request_denied` events keyed in process memory by effective client, status, method and route. It stores no client address or raw token in event details; a valid denied token is identified only by its stored token prefix as `actor_ref`. Specific Basic-auth audit events suppress duplicate generic denial events. The main REST inventory is in [`API.md`](../API.md). MCP wrappers are in `mcp_server.py`; they forward through the same API rather than querying SQLite directly. Their names, arguments and permission notes are listed in [`MCP.md`](../MCP.md).

The hidden `POST /api/admin/observability/mcp/invocations` receiver in `main.py` accepts only an MCP-designated bearer token and one of the registered bridge tool names. It records the tool name, outcome, elapsed milliseconds, one counter increment and one duration observation; it never accepts or stores arguments or result content. A bridge-generated random invocation ID becomes the event ID so retransmission is idempotent across an ambiguous timeout. The read-only MCP exception is limited to this exact write-only telemetry route and still requires API access and MCP to be enabled. The bridge's `_instrument_tool()` wrapper in `mcp_server.py` measures only outermost tools, preserves the original result, and retries failed reports from a local SQLite queue capped at 512 items/2 MiB within a 1.25-second network reporting budget plus short bounded local lock waits. The queue contains only the invocation ID, fixed tool name, outcome and elapsed time; it uses a per-user default path or an absolute `VAOS_MCP_TELEMETRY_DB` override. On POSIX it creates private new paths and refuses existing group/world-readable files rather than changing existing permissions; Windows relies on inherited LocalAppData ACLs. The oldest entry is dropped with a warning at the row limit. If the SQLite queue itself is unavailable, a bounded process-local fallback preserves best-effort retry but may be lost on process exit. The receiver deduplicates retries by invocation ID.

The hidden `GET /api/admin/observability/counter-queue` status route in `main.py` is available to a signed-in local administrator; bearer tokens also require the global sensitive-read setting and a token explicitly granted sensitive-read access. It returns counter queue counts, security-event fallback pending/drop counts and storage size without local paths, event details or dimensions. The result is explicitly scoped to the admin-process snapshot, reads stored queue state without probing write access, and does not observe unpersisted camera-worker memory; “No backlog observed” must not be interpreted as proof that writes succeed or that every process has no pending counts.

## CLI — `vaos_cli.py`

`build_parser()` defines `status`, `stats`, `logs`, `reports` and `integrations` commands. `Client.request()` uses the versioned API, HTTPS for remote origins, an environment API token or hidden password prompt, and bounded request timeouts. `_fetch_events()` handles bounded cursor pages for list/search/cat. `_fetch_tail_updates()` polls an inclusive timestamp overlap and follows API cursors up to a per-poll row limit; `_bounded_tail_seen()` retains at most 5,000 recent event IDs without splitting its timestamp boundary; `_write_tail_batch()` emits new events chronologically. A live tail stops visibly if the API reports more than 10,000 rows in one poll rather than pretending to have a complete stream. Follow mode supports text or NDJSON; JSON/CSV are snapshot formats through `--no-follow`. Command handlers format text/JSON/NDJSON/CSV and write local output. `main()` returns 0 for success, 2 for usage, 3 for authentication/authorization and 4 for service/local-file errors. It does not change VAOS state except for explicitly requesting a report job.
