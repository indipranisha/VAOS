# Observability storage schema

Observability data normally uses the existing VAOS SQLite database. Two private sidecars under `VAOS_DATA_DIR/.vaos-observability-fallback/` cover separate recovery cases: `counters.sqlite3` stores only aggregated API-request and inference-frame counters when the primary counter buffer is unavailable; `security-events.sqlite3` stores only the three allowlisted standalone login/authorization audit events when their primary audit/event/outbox transaction fails. Neither is a replacement for the primary database or a second application database. The security-event queue has its own schema version `1`, 10,000-row cap and 32 MiB page limit; its stable event IDs are replayed into the primary database. `observability_store.SCHEMA_VERSION` is currently `12`; the counter fallback has replay-payload version `1`.

## Tables

| Table | Purpose and key behavior |
| --- | --- |
| `vaos_schema_migrations` | Ordered schema version and applied-at ledger. |
| `observability_installation` | Singleton local installation identifier, first start time and schema version. It is not a cloud identity. |
| `observability_runtime_sessions` | Admin/camera lifecycle session, PID and private process-incarnation ID, start, heartbeat, clean stop/unknown state and app version. Schema v11 adds the nullable incarnation ID; legacy rows remain intact. |
| `observability_metric_catalogue` | Registered metric metadata and whether the source has produced observations. |
| `observability_events` | Bounded, redacted operational events, optionally linked to session/correlation; event-detail expiry follows the configurable policy (90 days by default). |
| `observability_counter_events` | Idempotent counter deltas keyed by source event; supports time-window totals. |
| `observability_lifetime_counters` | Durable lifetime counter totals, independent of event-text retention. |
| `observability_counter_buffer` | Synchronously persisted 10-second API/frame counter aggregates awaiting atomic conversion into normal counter events; it avoids one event row per request/frame. |
| `fallback_counter_buffer` (sidecar) | Up to 5,000 detailed 10-second API/frame aggregates plus one mixed overflow bucket per supported counter while the primary buffer cannot be written. |
| `fallback_counter_batches` (sidecar) | Up to 5,000 immutable batches awaiting replay. Deterministic event IDs and exact stored-payload checks prevent duplicate totals after a crash between primary commit and sidecar acknowledgement. |
| `fallback_store_metadata` (sidecar) | Sidecar schema version; unsupported versions are retained and rejected rather than silently discarded. |
| `observability_metric_observations` | Timestamped typed numeric observations with source event, dimensions, provenance, scope and estimate marker. |
| `observability_security_audit` | Append-only security audit with actor reference and previous/current integrity hashes. Update/delete triggers reject mutation. |
| `observability_report_jobs` | Bounded report request/status/output metadata; requester identity is omitted from public API responses. |
| `observability_export_audit` | Report download audit record, actor, report type, format and filters. |
| `observability_siem_destinations` | Disabled-by-default HTTPS JSON, Syslog TLS or OTLP destination metadata; event mapping and environment-variable reference only; key material itself is not stored. Archived destinations clear endpoint/credential references; `dropped_events` records delivery skipped at queue capacity. |
| `observability_delivery_events` | Unique destination/event delivery state, attempt count, retry/lease time, response status code and bounded error code. Terminal delivery history follows its configurable policy (90 days by default) and an overall 50,000-row cap; no more than 5,000 pending/retrying records are retained per destination. |
| `observability_saved_log_filters` | Up to 20 named filters per authenticated principal; stores bounded filter values with a SHA-256 principal namespace so separate accounts/tokens do not share saved searches. |
| `observability_gpu_energy_state` | Latest accepted measured GPU power sample and durable per-device integrated Wh, covered sampling seconds and skipped-gap count. Device IDs are installation-scoped hashes; raw GPU UUIDs are not stored. |
| `observability_retention_policy` | Singleton local policy for event-detail, metric-observation maximum and completed-delivery history retention. Defaults to 90/365/90 days; choices are 30, 90, 180 and 365 days. |

## Migration behavior

`initialize_database()` applies additive schema updates. The v4 migration adds the durable counter-buffer table and index. The v5 migration adds `event_format` to integration destinations with a default of `json`, preserving existing destinations. The v6 migration adds nullable `archived_at` and zero-default `dropped_events` fields for destination archival and bounded queue reporting. The v7 migration adds account-scoped saved Log Explorer filters without changing or deleting existing records. The v8 migration adds a composite actor-reference/time index for exact queries on the append-only security audit; it does not change or delete audit rows. The v9 migration adds per-device sampled GPU energy state. The v10 migration adds the singleton retention-policy table with defaults and preserves existing event, metric, audit, and application rows. The v11 migration adds a nullable process-incarnation identifier to lifecycle sessions. The v12 migration adds no application-data tables or columns: when a non-empty database is backed up and the additive schema change commits, it records one `storage.schema_migration_backup_verified` event and increments the lifetime `storage.schema_migration_backups` counter in the same transaction. The event includes only schema version, backup byte count and integrity result; it does not expose a filesystem path. Before a schema change to a non-empty database, `_verified_backup()` uses SQLite's online backup API to create an adjacent `backups/` copy, runs `PRAGMA integrity_check`, atomically renames the completed file, and writes a SHA-256 manifest. A failed backup prevents the migration from proceeding; a failed audit write rolls back the schema change. Empty/new databases do not claim a pre-existing-data backup. Migration tests use temporary databases only; the active VAOS database has not been opened or migrated for this work.

The feature does not drop existing application tables. Migration tests build temporary old-schema files, confirm a verified backup, then check that previous application data remains intact. Tests do not migrate the user's active database.

The fallback sidecars are created separately from the main-schema migration so sidecar setup failure cannot block VAOS startup. Their directory and databases receive restrictive current-account/SYSTEM permissions. The counter sidecar uses SQLite DELETE journaling (no persistent WAL files), FULL synchronous commits, at most 5,000 live detailed rows plus up to two mixed overflow rows, up to 5,000 pending immutable batches, and a 32 MiB database page cap. Reaching the logical cap preserves totals in a mixed bucket where possible; if the counter sidecar is full or unavailable, the existing 500-key in-memory fallback is used and may be lost on hard process exit. The security-event sidecar also uses DELETE journaling and FULL synchronous commits, with a 10,000-row cap and 32 MiB page limit; on saturation it increments a dropped-event count when that metadata write succeeds. If both primary and sidecar stores are unavailable, security audit retention cannot be guaranteed; accepted login remains fail-closed. The counter sidecar retains dimensions according to the existing counter-event retention behavior; delayed replay does not erase already aggregated counts. This delayed-retention behavior should be reviewed before exposing route-level metrics outside the local installation.

## Backup and restore

Use the normal VAOS backup procedure to copy the complete data directory while services are stopped or by using a consistent SQLite backup. **Include `.vaos-observability-fallback/` with the primary `app.db`**: pending aggregates and replay batches are not yet represented in the primary database and cannot be reconstructed from it. Preserve the directory and file ACLs. Project bundles remain configuration-only and must not include this operational queue. Protect database, manifest and any report outputs as sensitive local operational records. For a recovery drill, restore to a separate temporary data directory, verify the backup manifest hash and run `PRAGMA integrity_check` against both SQLite files when present. Never overwrite the active database during a test. See [deployment and rollback](deployment-and-rollback.md).
