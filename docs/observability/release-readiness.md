## Implementation summary

Feature 8 adds an admin-only observability page and API/MCP/CLI/report services to the existing VAOS source. It reuses VAOS authentication, SQLite, hardware telemetry and training callbacks. Schema migration is additive and the implementation takes and verifies a SQLite online backup before upgrading an existing non-empty database. External delivery defaults to off. When supported, NVIDIA board-power readings are recorded as measured watts and integrated into explicitly estimated GPU-board energy only across covered 20–90 second sample intervals; long gaps are reported and excluded, and no training-job attribution is claimed. Schema v10 adds configurable retention while preserving the 90/365/90-day defaults; schema v11 adds an internal process-incarnation identifier to distinguish quick restarts when an operating system reuses a PID, preserving legacy session rows through the verified backup migration path; schema v12 records verified pre-migration backup events and lifetime counts only when the schema upgrade commits.

The current report catalogue contains 14 types: lifetime statistics, operational events, security audit, lifecycle, metric history, training, reviewed-sample inventory, models, inference, cameras, tracking events, hardware/energy, API activity and MCP activity. CSV and PDF report jobs are bounded, provenance-aware and expire. The operational Log Explorer has literal text and exact optional correlation-ID filters, up to 20 authenticated-account-scoped saved filters; the separate restricted security audit supports exact actor-reference filtering. The Log Explorer has cursor pagination, an optional three-second live tail with pause, authenticated per-event links, filtered CSV/PDF reports through the central export service, and NDJSON capped at 1,000 events. Admin and camera HTTP middleware now accepts a valid `X-VAOS-Correlation-ID` or generates an opaque 128-bit ID, echoes it in the response, and binds it to request-scoped observability and security events. Background events without a request context can remain uncorrelated; these IDs are not distributed trace IDs. The terminal client supports status, metrics, logs, reports and integration status; metric counters can be grouped and exact dimensions filtered, with truncated results rejected.

The source implements signed HTTPS webhooks, RFC 5424 Syslog TLS and OTLP/HTTP JSON for redacted security events, with JSON/NDJSON, CEF and ECS-shaped mappings where applicable. OCSF is deferred until required privacy-safe actor/source data is available. Protocol construction is covered by mocked tests. Five loopback TLS transport tests exercise encrypted socket framing: four explicitly disable client verification, and one verifies rejection of an untrusted certificate. Two separate in-memory TLS handshakes confirm acceptance of a private trusted test certificate for its matching hostname and rejection of a mismatched hostname. No receiver interoperability or named SIEM vendor is evidenced. No SOPR command engine is included. Do not describe VAOS as SOC compliant or claim Splunk, Sentinel, Elastic or Wazuh compatibility.

## Known limitations

- Training telemetry is replayed oldest-first from the retained active JSONL file and up to 20 rotated segments (each rotates after roughly 1 MB) at startup, using idempotent event IDs. An OS-level sidecar lock now serializes append, rotation, and recovery reads across processes; a four-process Windows regression test preserves all 20 records through concurrent rotation. This bounds file count, not a strict byte ceiling: an oversized record can exceed the per-file threshold. Records older than that history, failed appends, and malformed/torn lines (counted and skipped during replay) can be lost. The in-memory event queue is also bounded, so a hard process exit before queued events reach SQLite can leave recovery dependent on the retained log. Local Windows behavior is tested, but target/network/cloud filesystem lock semantics are not. API/frame counters normally reach a durable primary SQLite aggregate before request completion. If that write fails, an allowlisted bounded sidecar SQLite queue stores aggregate counters in 10-second buckets (5,000 detailed rows, up to 5,000 replay batches, a 32 MiB database cap and mixed overflow buckets). If both SQLite stores fail or fill, each process uses a strict 500-key in-memory fallback; a hard exit before retry can lose those counts. The status endpoint is an admin-process snapshot, not a write probe or camera-process memory check. Hot-path lock waits are bounded in source but target-filesystem latency, disk-full behavior and lock-contention performance have not been measured.
- Actor references do not provide complete user/tenant attribution. Security audit, operational event and local SIEM outbox rows now share one SQLite transaction; a failed transaction is logged, but source attribution remains incomplete.
- Local Video Review contributes successful frame counts and separate sampled p50/p95 server-side processing latencies without storing file names, session tokens or frame content. The timing includes server-side queueing and processing, excludes browser upload/network time, and is not pure model/GPU inference latency. Target-hardware performance validation remains outstanding. Unknown energy remains unavailable rather than estimated from utilization.
- Legacy plain-text logs are not automatically imported; the event search uses literal text, not regular expressions.
- Request correlation is now propagated through admin and camera middleware: a valid caller value is echoed, while absent or invalid values are replaced with an opaque ID; request-scoped security and observability events inherit the ID. This is not a distributed tracing system. Dataset-preparation/import and model-training workers launched from a request inherit its ID; startup heartbeat/recovery, unrelated background or legacy events may remain uncorrelated. Actor, job and camera identities are not consistently available on every event.
- Actual TLS syslog/OTLP/HTTPS interoperability, vendor-specific adapters and SOPR commands are not tested or implemented. OCSF output is deliberately unavailable.
- Loopback HTTPS inspection on this Windows host substitutes a Norton “Untrusted Root” certificate, so successful payload-dispatch socket tests disable verification only in their test client. Strict trust and hostname behavior is separately exercised with `ssl.MemoryBIO`, but this does not prove verified socket delivery. Production TLS verification remains enabled; un-intercepted socket validation and real receiver interoperability remain release gates.
- DNS calls are bounded from the delivery worker by two daemon resolver workers, a three-second wait and an eight-request queue. The OS resolver call itself cannot be forcibly cancelled; if both workers stall, the bounded queue fills and subsequent deliveries fail/retry until resolution recovers.
- Editing a SIEM destination is now available in the page. Endpoint paths and credential references remain undisclosed; the administrator must re-enter the full endpoint when editing. Edits apply to pending and future events. API/service tests pass, but authenticated browser usability of the edit flow remains unverified.
