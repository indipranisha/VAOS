# Observability security and privacy

Observability is administrator-facing. It must not turn camera or biometric content into general-purpose logs.

## Data minimization

- Record event metadata, metric values and source/provenance only. Do not attach image/frame bytes, face embeddings/templates, participant names, raw camera tokens, capability URLs or model weights.
- Store actor references as bounded internal identifiers, not bearer secrets. Redact credential-like fields, URL query strings, local paths and sensitive JSON keys before saving event detail.
- Operational event content is bounded and expires according to the administrator-configurable event-details period (90 days by default). Metric-specific retention is defined in the catalogue and can be capped by the configured maximum. Lifetime counter ledgers and the append-only security audit are retained across routine retention cleanup.
- Hardware measurements are host operational data. GPU utilization is not proof that a particular model is actively using the device. GPU energy, when the device exposes power readings, is an estimate from sampled board-power values; it is not wall energy or job attribution. Raw GPU UUIDs are hashed before storage.

## Authorization

- The browser page uses the existing administrator Basic-authentication dependency.
- Versioned API calls use existing expiring scoped tokens. Observability reads are in the diagnostics group. Operational-event reads, security-audit reads and report export/list/status/download require the explicit sensitive-read option and a token granted sensitive-read access. The browser page uses the administrator Basic-authentication session.
- Saved Log Explorer filters are scoped to the authenticated Basic-auth username or API-token prefix through a SHA-256 namespace. They store only bounded filter values, not event results; do not put secrets into search terms or filter names. A different principal cannot list or delete another principal's filters.
- Integration changes use the control group. MCP calls pass through the same VAOS API policy and exact-request, single-use human approval flow for sensitive actions. This guide documents the intended protection; the report's test results must remain evidence-based.
- Outbound integrations are disabled until explicitly configured and enabled. Only HTTPS DNS endpoints on port 443 are accepted; all DNS answers must be public and the selected IP is pinned for the TLS connection. Resolution uses two daemon workers, a three-second caller timeout and an eight-item bounded queue; resolver stalls fail/retry rather than holding a delivery worker indefinitely.
- The external delivery outbox is bounded to 50,000 rows total and 5,000 pending/retrying items per destination. Terminal history expires according to the administrator-configurable delivery-history period (90 days by default) and may be evicted earlier to honor the total cap. If pending capacity is exhausted, the local event remains but the external send is skipped and a per-destination drop counter increments.
- For application security events, the append-only audit row, matching operational event and local outbox rows are committed together in one SQLite transaction. If the transaction fails, those writes roll back together and the caller records the failure; this does not make a database or disk failure recoverable by itself.
- Removing a destination archives it, clears its endpoint and credential reference, and disables pending deliveries while preserving the destination/event audit trail. An already in-flight send can finish; the UI warns before the action.

## Authentication event behavior

Accepted HTTP Basic credentials emit `auth.login_succeeded`; invalid credentials emit `auth.login_failed`. Basic authentication is sent with requests rather than establishing a durable browser login session, so these events mean “credentials accepted/denied for a request,” not proof of a new interactive session. To keep routine page/API use from flooding the append-only audit and SIEM queue, repeated results from the same effective client address are coalesced for 60 seconds in process memory. The coalescing map holds at most 512 addresses and evicts its oldest entry at capacity; exceptionally high distinct-client traffic can therefore cause an earlier repeat event. A failed attempt resets that address's success coalescing window. The address is used only as the in-memory key and is not written into the event; credentials and submitted usernames are never recorded. Failure events are likewise coalesced, and the existing rate limit remains in force.

Otherwise-unhandled HTTP 401 and 403 responses also emit `authz.request_denied`, so missing/invalid credentials and requests rejected by route permissions are visible to the security audit and optional SIEM queue. A more specific Basic-auth event suppresses a duplicate generic event. Repeated denials are coalesced for 60 seconds by effective client address, status, method and route template (or a redacted path fallback) in a process-local map capped at 512 keys. The address is only part of the in-memory key. Event details contain the status, method, route and a coarse denial reason; they do not contain the address, request body, query string, credentials or raw token. When a valid API token is denied by scope, its stored 14-character token prefix may appear as the actor reference; the fallback sidecar rejects a full token or any actor reference outside the three expected local identities/token-prefix form.

If the primary audit/event/outbox transaction fails for these three standalone authentication events, VAOS attempts to queue the redacted record in a private `.vaos-observability-fallback/security-events.sqlite3` sidecar. The sidecar is capped at 10,000 rows and 32 MiB and is replayed on startup and the observability heartbeat using the original event ID; a committed primary write with a lost response is therefore deduplicated. The status route exposes only availability, pending/drop counts and size. A successful login is denied with a sanitized 503 if neither primary nor fallback storage confirms the accepted-login audit. If the sidecar is also unavailable/full, the event can still be lost; the fallback does not protect against loss of the whole volume and OneDrive/network-filesystem durability is not verified. Back up the sidecar together with the matching VAOS data directory.

## Integrity and limits

The local security audit chain detects changes to rows while the chain and key ordering remain intact. It is not cryptographic proof against an administrator with full filesystem/database replacement rights. Store backups with separate access controls.

CSV formula prefixes are escaped. Reports have row, byte, date-range, concurrency and expiry limits. PDF text is clipped for page layout. External delivery supports public HTTPS, certificate-validated Syslog TLS, and OTLP/HTTP JSON only; destinations are disabled by default and constrained to public DNS addresses on fixed ports. Webhook payloads use HMAC; OTLP bearer tokens are referenced from the service environment. The optional `VAOS_SIEM_CA_BUNDLE` setting adds a service-admin PEM CA bundle to platform trust without relaxing certificate or hostname verification; invalid configuration fails closed. Destination listings omit endpoint paths and credential names. Protocol/format mapping tests use mocks; vendor receivers remain untested. OCSF is unavailable until source fields support truthful schema-valid events. Never expose a destination path or secret value in screenshots or support tickets.

## Incident response

If a key or API token is exposed, revoke/rotate it in the secret manager and VAOS settings, disable affected destinations/tokens, review the audit history, preserve relevant database backups and re-enable only after checking destination and scope. Do not include secret values in an issue report. See the root [SECURITY.md](../../SECURITY.md) for vulnerability reporting.
