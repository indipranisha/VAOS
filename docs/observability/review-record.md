## Disagreement and resolution

- **Protocol support vs. receiver interoperability:** The source implements signed HTTPS JSON/NDJSON/CEF/ECS mappings, RFC 5424 framing over TLS, and OTLP/HTTP JSON logs. Mocked tests cover these paths. OCSF was reviewed against the official 1.9.0 schemas but is not selectable because current source events lack required actor/source data. No real syslog collector, OpenTelemetry Collector or named SIEM vendor was accessed; receiver interoperability and vendor compatibility remain unverified. SOAR commands remain unsupported.
- **“Lifetime uptime” vs. uncertain process exit:** A missing heartbeat cannot establish crash time. Unknown sessions are marked unknown and contribute only through their last heartbeat; summaries disclose this lower-bound quality.
- **Energy analytics vs. no power sensor:** CPU/GPU utilization is not a watt reading. Energy remains unavailable instead of estimating from utilization.
- **Browser acceptance vs. resource safety:** During the initial review, no extra server or model was launched because the runtime was older than source and a prior training run had failed under high memory pressure. A later isolated Uvicorn smoke used a unique temporary database and no model/camera workload. It exercised core Statistics & Observability page controls; full personas, accessibility/responsive checks and runtime-source identity remain release blockers.

No security penetration test, real receiver interoperability test, actual browser personas, comprehensive accessibility audit, production database restore, whole-app performance benchmark, or external review was performed. Do not treat this record as a pass for those gates.

### SIEM lease and documentation follow-up review (12 November 2026)

The bounded resolver prevents one stalled DNS call from blocking a delivery worker indefinitely, but its daemon worker remains occupied until the operating system resolver returns. Resolver saturation and receiver-accepted-before-status-update behavior remain release fault-injection/interoperability gates.

### Authentication event coverage follow-up (12 November 2026)

### Durable MCP invocation telemetry queue (14 November 2026)

The previous bridge kept retry reports only in memory, so an MCP-host restart could discard otherwise valid call metrics during a VAOS outage. The bridge now writes only the random invocation ID, registered tool name, success/error outcome, and bounded duration to a per-user SQLite queue capped at 512 rows and 2 MiB. A successful API response is followed by a local delete; if the response is ambiguous, the same ID is retried and the receiver deduplicates it. A stale process can therefore leave a queue for a new bridge process to resume without storing arguments, results, API tokens, images, or request payloads. On POSIX, newly created queue paths are private and existing group/world-accessible paths are rejected without changing their permissions; Windows relies on inherited LocalAppData ACLs, which have not been validated on a production account. If local SQLite is unavailable, the bridge retains a bounded volatile queue and still preserves the tool result.
