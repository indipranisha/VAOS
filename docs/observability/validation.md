### Schema v12 verified-migration-backup observability (13 November 2026)

- Added the `storage.schema_migration_backups` lifetime counter and `storage.schema_migration_backup_verified` event. For a non-empty database, the event is written in the same transaction as the migration version only after `_verified_backup()` has produced a verified backup. The record contains schema version, byte count and integrity result, but no filesystem path. Fresh databases do not claim a pre-existing-data backup; a failed or missing backup blocks migration, and a failed audit write rolls the schema transaction back.
- Regression checks assert one event/count after an upgrade, no duplicate on repeat initialization, no fabricated backup record for a fresh database, preservation of existing data when backup/audit recording fails, and documentation/catalogue parity. A dedicated v11-to-v12 fixture verifies old observability events remain in both the upgraded database and pre-migration backup, while the new event/counter appears only after upgrade. The authenticated metric catalogue, counter-series query and event-list APIs expose the upgrade record and total. The focused storage suite most recently passed **48 tests in 15.146 seconds**; the complete isolated repository suite passed **254 tests in 55.900 seconds**. Test databases and backup files were temporary; the live VAOS database and services were not opened, migrated, restarted or modified. This is migration-path evidence only; representative production restore/cutover, target ACL/filesystem behavior, hard-crash and full release gates remain open. Staging remains **NO-GO**.

### Retention GET/PUT race and audit-write follow-up (13 November 2026)
